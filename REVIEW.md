Phase 1: Universal evidence integration (scanner, investigation, Retro-Hunt, reports, UI)

What exists now. One evidence vocabulary and one evidence module: investigation_agent.py. Scanner observations are structured evidence (IDs S1.., built by build_scan_evidence, stored additively in result["evidence_register"], with machine findings SF1.. in result["scan_findings"] and result["scan_id"], plus result["origin_intel_status"] recording whether the optional origin engine was ok, unavailable or failed). Investigation evidence keeps its E1.. IDs and gains type, source, origin, source_reference, observed_utc and scan_id; tool findings gain IF# IDs and AI findings AF# IDs with a verification label. Origins: direct_machine, trusted_external, untrusted_claim, historical, inference. scan_id = "SC-" + the first 32 hex characters (128 bits) of the SHA-256 of the original bytes (an identifier, not content; identical bytes give the identical id). IDs are unique per register; S# (scanner) and E# (investigation) cannot collide, and qualified_id() gives "<scan_id>/<id>".

Check outcomes are distinguished by status: ok (completed), partial (completed, incomplete coverage), missing (the expected output is absent, cause unknown), unavailable (the component or feed that would produce it is not available), skipped (deliberately not run) and failed (it ran and errored, or returned malformed output). A missing, malformed or failed geo / IOC-extraction / origin_intel / community output is never recorded as a successful zero-result check; each gets non-ok evidence and an "uncertain" finding. Community intelligence is OFF by default and is not recorded at all when disabled (it is not a failure); when enabled but unavailable, errored or malformed it is recorded as unavailable or failed. validate_scan_register() type-checks every value before using it as a key, requires evidence ids S#, finding ids SF# and scan ids SC-<32 hex> (or "" for an unidentified scan), and never raises; build_report/scan_evidence_md render a malformed register from its well-formed parts and say it failed validation.

Guarantees (each covered by test_evidence_integration.py): the scanner's score, level, verdict, model output and every pre-existing result field are unchanged (golden values captured from the pre-change code; the evidence step is pure and a builder fault only sets evidence_error); only what a detector actually reported becomes evidence; missing, failed or malformed checks become evidence with status missing/failed and an "uncertain" finding, never a clean result; a "suspicious" finding never cites missing/failed evidence; header values are untrusted_claim unless the scanner itself marked every authentication mechanism verified; GeoIP is an approximate inference; no body text, full address or URL path is copied; AI findings may cite only evidence IDs of their own investigation (unknown, foreign-scan and scanner S# IDs are rejected), stay secondary and cannot change scores; an investigation from another scan is detected (check_scan_binding) and is not rendered or shown; Retro-Hunt evidence is origin "historical" with the hunted indicator, match basis (exact/subdomain), recorded source and source class, first/last seen and tier, and the current scan's own records stay excluded.

Reports. Machine forensic report (report.build_report, section 9, and the Dossier machine_md), combined report (machine + AI) and batch reports (per-email build_report) carry the scanner evidence register and machine findings. The agentic investigation report (render_report) carries an investigation evidence register defined once, findings that keep their [E#] references plus finding ID, verification and origin, and a scan binding row. UI: Classification panel expander (scanner register); investigation panel shows evidence IDs, finding IDs, verification and provenance next to findings, lists AI-proposed findings in a separate "secondary" group, adds an Evidence register view, and discards a stored investigation that belongs to a different scan.

Phase 2: Attack DNA / Campaign Fingerprinting (new: attack_dna.py)

What exists now. A new, separate module, attack_dna.py, recognises potentially related campaigns from the structural/tactical shape of an email rather than literal shared indicators, so it tolerates an attacker rotating domains/IPs/hosting. The fingerprint is exactly five feature families, each a set of categorical tags: auth_anomalies (which header-analysis anomaly titles/severities fired), url_tactics (which URL-building tricks were flagged: shortener, raw-IP host, punycode, brand look-alike, suspicious TLD, credential-path, deep subdomain, unencrypted HTTP), domain_alignment (whether reply-to/return-path disagree with the From domain, and whether the sender is a freemail address), infra_class (the geolocated origin's coarse infra label plus country), and structural (coarse body-length/URL-count/attachment-count buckets plus HTML-vs-text). It is additive and separate from correlate.py (exact shared indicators) and retro_hunt.py (exact indicator history); neither file was modified, and a test (test_attack_dna_does_not_duplicate_correlate_or_retro_hunt) confirms attack_dna is not referenced by either.

Pipeline: analyzer.analyze_email() computes result["campaign_fingerprint"] and result["campaign_matches"] once, before calling investigation_agent.build_scan_evidence() (same ordering as every other Phase 1 signal: pure computation first, evidence-building reads the precomputed result). build_scan_evidence()'s new "campaign fingerprint" section reads only those two fields and performs no database access itself (test_build_scan_evidence_reads_precomputed_fields_only patches tracker.get_connection to raise and confirms the section still runs). Findings use only the pre-existing _FINDING_KINDS vocabulary ("verified"/"suspicious"/"uncertain" -- no new kind was added): "suspicious" for a strong match, "uncertain" for a weak match, no match, or when fingerprint/history data is unavailable. Every cited evidence id is verified to exist in the register by the same contract test_investigation_agent.py already enforces elsewhere.

Classification safeguards, enforced in code and covered by dedicated tests: a "strong" classification requires overlap in >= 2 of three "specific" families (auth_anomalies needs >= 2 shared anomaly tags, url_tactics and domain_alignment need >= 1) AND a weighted score above threshold; infra_class (hosting/ASN/country) and structural (size buckets) can add weight but can never by themselves satisfy the independent-families requirement, so shared hosting/ASN/IP-prefix alone can never reach "strong" (test_shared_hosting_or_asn_alone_cannot_produce_a_strong_match). A single shared generic auth anomaly also cannot qualify its family (test_single_generic_auth_anomaly_alone_does_not_qualify_the_family). A missing or malformed feature family on either side is excluded from comparison entirely -- it lowers `confidence`, it is never scored as a match (test_missing_or_malformed_evidence_degrades_gracefully, test_one_sided_missing_family_lowers_confidence_but_never_matches_on_it). Every finding text was checked to avoid asserting common authorship ("not confirmed common authorship"; no finding text contains "same attacker").

Privacy and storage. tracker.get_connection(shared=...)'s actual scope was read (tracker.py's _db_path()) before use, not assumed: shared=True always resolves to the single pooled threat_memory.db (nomic_embed.py's existing, intentional choice for its own table). shared=False -- attack_dna's default, and never overridden by anything in its own call path -- is session-scoped persistence only when SIH26106_MULTIUSER is on: each visitor session then gets its own, separate sqlite file, keyed by that session's id, invisible to every other session. Phase 3: Campaign Intelligence (new: campaign_intel.py) -- newly written documentation

Provenance of this section. The Phase 3 documentation that an earlier revision of this file is believed to have contained was not present in any archive available when this section was written, so it could not be restored. This section was written fresh from the current code and from test runs performed in this environment; nothing below is copied from the lost original, and it describes only what was checked.

What exists now. campaign_intel.py is a pure module that reorganises data Attack DNA (Phase 2) has already computed for a scan -- the scan's fingerprint, its top matches and the bounded history rows read by that same find_matches() call -- into an analyst-facing summary: related retained observations, the specific feature families supporting each relationship, tactic changes (tags added/removed, shown only where both observations had data for that family) and a category-level infrastructure comparison (class and ISO country tags only; missing data on either side is reported as \"unavailable\", never \"changed\"). Classification, score and confidence are Phase 2's compare_fingerprints() values passed through unchanged; there is no second score or confidence formula and nothing upgrades a relationship. infra_class and structural are reported as context only and never counted as independent support. The timeline is distinct retained observations ordered by storage time (created_at); it is not every scan, not send dates and not attack events. The module performs no database, network or UI access and does not mutate its inputs.

Integration. analyzer.analyze_email() calls campaign_intel.build_campaign_intel() immediately after attack_dna.find_matches(), passing the history rows that same call already read (no extra query), inside its own try/except; on any exception result[\"campaign_intel\"] is None. investigation_agent.build_scan_evidence() gains a \"campaign intelligence\" section that reads only result[\"campaign_intel\"]; every finding it emits is \"uncertain\" and states shared tactics, not confirmed common authorship. report.campaign_intel_md() renders a read-only Markdown table (never raises; empty when there are no related observations). app.py shows a table under the existing Attack DNA panel built from the precomputed result and campaign_intel.tactic_summary().

Hardening. Stored fingerprint JSON is not trusted: campaign_intel exposes a tag only if it fits its family's known vocabulary. url_tactics and domain_alignment tags must be members of fixed sets; infra_class must be a known class or a country: tag with a real ISO 3166-1 alpha-2 code; structural tags must match a small len/urls/attach/html pattern; scan ids and timestamps must match strict patterns; malformed Phase 2 fields are range-checked or dropped. In this follow-up, auth_anomalies validation was tightened from a pattern (any known severity followed by up to 60 free-form characters, which let dynamically generated titles through) to an exact allowlist, _AUTH_TAGS, of 19 \"severity:title\" strings: the twelve high:<SPF|DKIM|DMARC> <fail|softfail|permerror|temperror> tags plus the seven fixed header_analysis.py titles that Attack DNA retains (with Reply-To on a related subdomain allowed at info and low, the two severities header_analysis.py assigns it). The five absence/unknown titles that attack_dna.py already excludes at extraction are not in the allowlist. attack_dna.py and its extraction semantics were not changed. test_campaign_intel.AuthTagAllowlist adds four tests: every non-excluded title found in header_analysis.py's flag() calls must be in the allowlist (a drift guard); real extraction output survives validation; about twenty arbitrary, dynamic or malformed strings (wrong severity, case or whitespace variants, IPs, emails, URLs, trailing text, non-strings, the absence titles) are rejected; hostile tags never reach tactic_changes output.

Phase 4: Entity Graph (new: entity_graph.py) -- final verified status (after review corrections)

Scope. Phase 4 adds a session-scoped, evidence-linked Entity Graph on top of Attack DNA (Phase 2) and Campaign Intelligence (Phase 3), both unchanged. Attack DNA was verified, not modified: it provides fingerprint extraction, comparison with generic-tag vetoes and per-session storage; it does not fingerprint message wording, formatting or payload and has no separate "partial" class. Adding those would change Phase 2 semantics and remains open for a separately approved change.

Placement. The code lives in entity_graph.py, not correlate.py (approved deviation, to be kept): correlate.py imports plotly at module level and the scan path must not depend on a plotting library. correlate.py is byte-identical to the starting archive.

What it does. Relationships Email -> Sender -> Domain -> IP -> URL -> Campaign are derived from what the scan already produced: sent by, at domain, from domain, replies to, return path, links to, at host, originated at, fingerprinted as, similar tactics to. Each edge carries entity ids and types, relationship, basis (observed or inferred), cited evidence ids, provenance, confidence, observation time and, for similarity edges, the original Phase 2 score and matched scan id. An edge exists only if the evidence it cites is in THIS scan's register; otherwise it is skipped and counted, never invented. Basis follows the cited evidence (inference or historical gives inferred, otherwise observed; header values stay untrusted_claim in provenance). A campaign node is the Attack DNA fingerprint of one retained scan, not an attributed actor; no edge states ownership or common authorship and no model-generated text is used (explanations are assembled from the edge's stored fields and the cited observation).

Review correction 1 -- evidence attribution. Before: one combined header entry (From/Reply-To/Return-Path domains) was cited for every sender and domain edge, and nothing supported the sender address at all. Now investigation_agent.py records one evidence entry per claim (From address with the local part withheld, From domain, Reply-To domain, Return-Path domain; type header, source email_parser, origin untrusted_claim, metadata claim and domain). Each edge cites exactly its own entry, and the entry only counts if its source reference, claim kind and recorded domain all match the value the edge is about; sent by and at domain cite the address claim, from domain / replies to / return path cite theirs. The combined entry is never cited. The new section sits after the Phase 2 fingerprint section and before Phase 3 campaign intelligence (that section's existing test requires it to stay last); every Phase 0-2 evidence id is unchanged, and campaign-intelligence ids now come after the claim entries (up to four higher than before). Evidence ids are generated per scan and nothing stored depends on the old numbering. A register without claim entries (older results) loses only those edges and says so.

Review correction 2 -- stale persistence. Before: a scan that now yielded no edges returned early and left its old edges stored. Now a scan's edges are always replaced by what the CURRENT register supports, including an empty set, in one transaction. Evidence-generation failure (builder error, missing or malformed register, register of another scan, no scan id) is handled separately: status insufficient_evidence, nothing is deleted, and the number of earlier edges kept is reported as possibly out of date. A register that is present but backs none of the relationships found in the message gives insufficient_evidence (relationships_unsupported) and replaces the old edges; a register that is usable with nothing to link gives the valid empty status no_edges and clears them. A cleared scan no longer appears in other scans' history.

Review correction 3 -- failure transparency. Seven distinct statuses: ok, no_edges, insufficient_evidence, unavailable, key_unavailable, persistence_failed, error. entity_graph.status_message() is the single source of the text used by the app and the report, and only no_edges says no relationships were detected. persistence_failed shows the derived edges but states they are unsaved; it also covers multi-user mode with no identifiable session, where tracker falls back to a throw-away in-memory database (previously that would have looked saved). The app shows st.error / st.warning / st.info; the report adds a labelled banner. A result with no entity_graph key (older scans) shows nothing; an explicit None (builder failed) says the graph could not be computed.

Review correction 4 -- visualization (assessment and result). correlate.graph_figure() draws only node kinds in its NODE_STYLE and styles edges by REL_STYLE, so the new kinds would have been invisible. entity_graph.to_correlation_graph() adapts the stored edges (plus other retained scans that share an entity) to that shape without touching correlate.py: email -> case, sender -> email, domain, ip, URL -> infra, campaign -> semantic; parallel relationships merge into one label, inferred edges say "(inferred)", similarity edges carry the Phase 2 score. app.py draws it with the existing _render_correlation_figure() inside an "Connected graph (visual)" expander, fail-soft, below the tables (which remain the complete record). The multi-edge NetworkX view entity_digraph() is kept. Verified here only by running the real graph_figure() code against a recording fake of plotly; real drawing in Streamlit is NOT verified. Hover text shows the mapped style kind (for example "infra" for a URL), inferred relationships use the neutral edge colour, and the Streamlit panel itself has never been rendered.

Review correction 5 -- isolation against the real tracker. test_entity_graph.RealTrackerIsolation runs tracker.py's own _session_id(), _db_path(), get_connection(), delete_my_data() and idle-session cleanup unmodified; only SESSION_DIR, DB_FILE and MULTIUSER are redirected to a temp directory, and Streamlit's script-run context (absent here) is faked at the import boundary so tracker decides which file each visitor gets. It checks distinct files per visitor holding only their own scans, different per-session keys and entity ids for the same domain, no graph tables in the shared database, session file mode 0600 / directory 0700, the same visitor still correlating, no-session fallback reported as unsaved, delete-my-data and TTL cleanup removing the graph and its key together, and two concurrent threads not seeing each other. tracker.py was not modified. A real Streamlit session was not exercised.

Review correction 6 -- URL evidence (final review finding). Before: a URL relationship fell back to the aggregate "URLs extracted" evidence entry when the URL had no entry of its own, so an unflagged URL, or a flagged URL beyond the register's per-item limit (individual URL evidence exists only for the first eight flagged URLs), could receive an edge supported only by counts that do not identify any URL. Now "links to" and "at host" each require the exact per-item entry for that URL (type URL, source ioc_extract, status ok, source reference result.iocs.urls[<its index>]) whose recorded host equals the host of the URL string itself (not the extractor's separate host field); the aggregate entry is never cited. A URL without such an entry produces neither edge; each skipped relationship is added to skipped.no_evidence, so the app and report say relationships were left out, and nothing for it is stored (a rescan that loses the per-item entry removes the stored URL edges). Only the host is ever stored: no URL path, query string or token. Changed: entity_graph.py (one lookup function replacing the fallback) and test_entity_graph.py (+9 tests: unflagged URL with only aggregate evidence, ninth flagged URL, host mismatches in three forms, valid per-item evidence citing each URL's own entry, entry validity (source, status, type, index, metadata), aggregate never cited, stored edges removed when evidence is lost, scan with only unsupported links not reported as clean, host-only persistence). No Phase 2, scoring, calibration, feedback, contribution or Supabase file changed.

Persistence and privacy (unchanged design). Tables entity_edges and entity_meta are created at runtime in the visitor's own database via get_connection(shared=False); no Supabase migration, no flag change. Entity ids are HMAC-SHA256 of the normalised value under a random per-session key; if the key is missing or corrupt while edges exist the graph reports key_unavailable and writes nothing (never silently regenerated). Sender addresses, email bodies, URL paths and queries, and private or reserved IPs are never stored; only domains, public IPs, URL hosts and opaque scan ids carry readable labels. Edge count is capped at 20000, oldest first.

Integration. analyzer.analyze_email() builds the graph after the evidence register inside try/except (explicit None on failure) and never touches a score or verdict. report.py shows the section after Campaign Intelligence; its shared-entity table is counts only, because an existing test keeps other scans' ids out of a scan's report. app.py shows tables, the status banner and the visual graph.

Global learning compatibility. classifier.py, tracker.py, contribution_client.py, admin_review.py, review_tool.py, rebuild_model.py, nomic_embed.py, config.py, risk.py, retro_hunt.py, attack_dna.py, header_analysis.py and supabase/ are byte-identical to the starting archive, and a test asserts entity_graph.py never references feedback, classifier, contribution, shared-indicator or semantic-origin storage.
